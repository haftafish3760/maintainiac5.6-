# Parser QA Platform Plan

Scope: reusable parser QA platform plus the current Work Supplies inventory parser adapter, catalog intelligence, trade-pack parsing knowledge, and privacy-safe parser QA reporting.

This is not supposed to be a one-off inventory-only harness. The shared platform layer must stay reusable for future parsers such as maintenance, invoice/estimate/job material import, support-ticket parsing, and other text-to-structured-data flows. Inventory is the first heavy adapter because it has the most immediate trade-pack/catalog work.

Hard boundary: this harness must not modify or depend on OCR, camera, PDF, Expenses, Firebase, jobs, invoice UI, dashboard, or platform-specific device APIs. It tests parser brains after text already exists.

UI can move, but parser contracts must not. Do not write detailed UI/widget QA for unfinished screens in this parser harness. Parser/catalog QA should validate data contracts, review-only candidates, routing metadata, source-of-truth rules, fixture behavior, privacy/security boundaries, and reusable harness behavior. Screen layout, widget placement, navigation visuals, and golden UI checks belong in a later UI-specific milestone after the target screen is stable.

Firebase writes are still off-limits in parser QA, and no live hosted writes in tests are allowed. Local pack mode is the default for parser harness work; Cloud fallback must remain opt-in, separately approved, and outside smoke/full/release parser QA until a future integration profile exists.

## Harness Goals

- Run large parser QA batches in one process instead of launching many tiny Flutter shards.
- Preserve accuracy while making local iteration fast enough for hundreds or thousands of cases per pass.
- Produce grouped failures with suggested fix categories instead of unreadable dumps.
- Keep shared QA orchestration reusable across parser domains; domain-specific adapters provide fixtures, schemas, expected-result contracts, and category-specific risk rules.
- Classify every failure into a triage category such as schema, alias, merchant rule, conflict, normalization, category, unit, quantity, confidence, context, parser engine, privacy, security, performance, governance, review safety, fixture, economics, locale, or baseline.
- Keep failure taxonomy explicit, including unknown, so every reported parser QA failure has a stable category and suggested fix path.
- Support report-only local runs and strict release-gate runs from the same suites.
- Keep the harness cross-platform so it can run on Windows, macOS, Linux, CI, and the Mac Mini.
- Keep QA reports privacy-safe: no full private receipts, card numbers, customer names, addresses, phone numbers, auth codes, or payment identifiers in future telemetry/admin reports.
- Keep harness files maintainable: 500-line preferred target for Dart harness files and a 1000-line hard ceiling unless a future pass explicitly refactors the file or documents why no safe split exists.

## Storage Layout

Inventory-specific pieces should remain in the work-supply adapter layer: trade-pack matrices, item schema rules, catalog blueprint generation, merchant/alias recipes, and inventory parser fixtures.

Each report includes run configuration provenance plus `slowestSuites` and `QA_SLOW_SUITE` summary lines. The JSON `runConfig` object and text `QA_RUN_CONFIG` line record the active profile, preset, suite filter, baseline path, generated-case limit, failure cap, catalog schema sample limit, and alias sample limit so a report can be reproduced without guessing which knobs were used. Use the slow-suite data to separate harness/runtime bottlenecks from parser accuracy work before changing batch sizes or test strategy.

Full/release shard runs also record `PARSER_QA_SHARD_ID`, `PARSER_QA_TIMEOUT_BUDGET_MS`, and `PARSER_QA_RESUME_FROM` through the same `runConfig` path. This keeps each shard artifact tied to its shard id, suite filter, generated-case limit, timeout budget, and resume evidence instead of relying on memory or terminal scrollback.

Use `flutter test test/work_supply_parser_generated_fixture_runner_test.dart --dart-define=PARSER_QA_GENERATED_FIXTURE_PATH=build/parser_qa_generated/work_supply_parser/plumbing/residential/core/en-US/generated_fixtures.json --dart-define=PARSER_QA_GENERATED_FIXTURE_MAX_CASES=500 --reporter compact` to run a generated batch through the parser in one local Flutter process. This is the economical parser-call path for generated fixture batches; leave `PARSER_QA_GENERATED_FIXTURE_PATH` empty for normal no-op smoke. For surgical reruns after a generated fixture failure, add `--dart-define=PARSER_QA_GENERATED_FIXTURE_IDS=<comma-separated-fixture-ids>` so only the failed fixture ids are selected from the file. The runner writes timestamped JSON plus `latest_generated_fixture_run.json` under `build/parser_qa_reports/generated_fixtures/`, or under `PARSER_QA_GENERATED_REPORT_DIR` when that override is supplied.

For handoff between this Windows machine, GitHub, an external SSD, and the Mac Mini, treat the pass log plus latest report aliases as the resume point. Do not rely on terminal scrollback. Push or copy the repository only after the latest pass is logged, `git diff --check` is clean for touched files, and the intended focused/quick command evidence is captured in the pass log.

Quality gates must run non-interactively by default. Start analyzer, QA runner, build, lint, and focused quality-gate commands, wait for process completion, then inspect the exit code and summarize only actionable results. Do not continuously narrate terminal scroll, percentages, or individual passing tests. Switch to live monitoring only if a command becomes interactive, requests input, stalls unexpectedly, or exits with an error. Do not rerun analyzer, QA runner, or full quality gates unless source files affecting those checks changed after the last successful run.

catalog-backed suites should be grouped at meaningful checkpoints to amortize the cold catalog load. contract-only suites stay surgical and should run by exact `PARSER_QA_SUITES` filters. Do not repeatedly launch one catalog-backed suite at a time unless the changed source is isolated to that suite and the slow evidence is needed.

Each report also includes failure triage data. JSON output carries `triageCategory` on each failure and a `failuresByTriageCategory` group. Text summaries include `QA_TRIAGE_GROUP` lines and each `QA_FAILURE` line includes `triage=...`, so admin/debug tooling can separate schema work from alias work, security work, review-safety work, performance work, and parser-engine work without reading every failure manually.

Each report includes `packHealth` JSON and a `QA_PACK_HEALTH` summary line. The shared report writer also emits `latest_<domain>_pack_health.json` so admin/debug tooling can read pack readiness without parsing the full QA report. The health object includes present contracts, missing required contracts, missing recommended contracts, `healthScore`, `coverageScore`, `readinessLabel`, checked count, failure count, and duration.

Each run writes a timestamped report plus a latest alias under `build/parser_qa_reports/`, which is ignored by Git through `/build/`. Timestamped reports preserve run history for local diagnosis, while latest aliases keep Command One/admin and developer tooling pointed at the newest evidence without scanning every file.

## Parser Platform Pillars

These pillars are the non-negotiable architecture checks before bulk catalog expansion. The harness must keep them visible because the parser has to behave like a platform, not a pile of aliases.

- Environment-independent parser core: the parser engine must not know whether it is running on the user's phone, backend, test harness, command-line tool, or cloud service. It must accept pure parser input such as OCR text, enabled trade packs, parser settings, merchant/context hints, locale, and user-confirmed context, then return pure parser output such as parsed candidates, confidence, review status, warnings, evidence, and suggested actions. Mobile adapter, server adapter, QA harness adapter, and batch parser adapter code may wrap the engine, but the core parser must not depend on Firebase, Hive, Flutter widgets, camera/OCR APIs, network calls, file paths, device state, or cloud platform specifics. Owner suite: `inventory.parser_platform_contract`.
- Review-only parser result: every stage writes evidence into a review-only parser result, and Nothing auto-saves. Owner suites: `inventory.result_contract` and `inventory.review_safety_contract`.
- Fast local harness: large parser QA batches in one process plus a fast non-Flutter parser test harness keep iteration economical. Owner suites: `inventory.runtime_profile_contract`, `inventory.runtime_measurement`, and `inventory.execution_command_contract`.
- UI-independent parser contracts: UI can move, parser contracts must not. Do not write detailed UI/widget QA for unfinished screens; keep parser QA focused on stable data contracts and enforce this through `inventory.boundary_guard`.
- Golden and generated fixtures: golden fixtures plus generated risky receipt-line families prevent overfitting to happy paths. Owner suites: `inventory.golden_fixtures` and `inventory.generated_cases`.
- Ground-truth dataset governance: every fixture and reviewed dataset needs a source owner, source type, synthetic/real flag, review date, expected-answer confidence, locale, merchant, and trade context so bad expected data cannot poison the parser. Owner suites: `inventory.fixture_governance`, `inventory.fixture_corpus_contract`, and `inventory.data_provenance_contract`.
- Independent validation set: maintain a holdout fixture set and validation strategy that prevents overfitting to visible golden fixtures. Differential baseline tests, changed-item impact mapping, metamorphic variants, property-generated cases, and deterministic repeatability must all stay represented before broad parser claims are accepted. Owner suite: `inventory.validation_strategy_contract`.
- Ambiguity-first ranked candidates: Ambiguity-first matching returns ranked candidates and keeps trade context visible instead of forcing unsafe guesses. Owner suites: `inventory.trade_context` and `inventory.separation_safety`.
- Merchant rule packs: Merchant rule packs capture store-specific abbreviations, department hints, and major merchant alias normalization. Owner suite: `inventory.merchant_rules`.
- Negative-match/conflict graph: Negative-match/conflict graph coverage keeps PVC plumbing, PVC conduit, HVAC drain PVC, tape, filters, boxes, and other overlap families separated. Owner suites: `inventory.alias_conflicts` and `inventory.dangerous_words`.
- Versioned pack intelligence: Versioned pack intelligence keeps chunk checksums, source confidence, generated/manual flags, health scoring, and pack readiness auditable. Owner suites: `inventory.pack_lifecycle` and `inventory.pack_health_score`.
- Pack recovery and disaster safety: corrupt pack, interrupted download, duplicate install, missing locale pack, missing chunk, unsafe path, checksum mismatch, and rollback/reinstall paths must fail safely before any hosted/local pack is accepted. Owner suite: `inventory.pack_recovery_contract`.
- Correction review pipeline: Correction review pipeline keeps user fixes local/reviewed first and requires manual promotion before official catalog or parser-pack changes. Owner suite: `inventory.correction_feedback_contract`.
- Device/storage strategy: Device/storage strategy covers local packs, not-enough-storage paths, old-phone limits, metered network warnings, and cloud fallback disclosure. Owner suite: `inventory.device_storage_contract`.
- Security/Firebase boundary: Security/Firebase boundary keeps parser QA local, privacy-safe, hostile-input tested, and with no live hosted writes in tests. Owner suites: `inventory.security_privacy` and `inventory.no_live_services_contract`.
- Legal and proprietary-data safety: Do not copy proprietary retailer catalogs, private receipt dumps, scraped SKU databases, or full private receipts into parser QA. Use synthetic fixture lines, generic merchant abbreviation patterns, reviewed public/manual source notes, and source metadata instead. No full private receipts belong in the harness. Owner suite: `inventory.legal_safety_contract`.
- Legal barcode/vendor provenance rules: `official_pack_mappings_require_licensed_or_public_source`, `retailer_database_scraping_is_forbidden`, and `merchant_sku_mapping_requires_source_confidence` must stay visible before barcode, UPC, GTIN, vendor SKU, or merchant item-number mappings can be used in parser QA or official pack promotion.
- Parser SLO and quality metrics: release claims must be expressed as measurable targets, including top-1 clear-match accuracy, top-3 ranked-candidate accuracy once possible matches exist, false-confident rate, receipt-noise false-positive rate, review/unknown rate, runtime budget, cost/privacy telemetry budget, and Command One/admin visibility. Owner suite: `inventory.slo_metrics_contract`.
- Admin-safe observability: admin-safe report output supports Command One diagnostics without raw receipt text, card data, customer names, addresses, or phone numbers. Owner suites: `inventory.admin_report_contract` and `inventory.telemetry_contract`.
- Portability and handoff: parser QA tools must stay runnable from Windows, macOS, Linux, CI, GitHub checkout, external SSD transfer, and the Mac Mini using relative paths, Dart/Flutter commands, ignored build artifacts, and logged resume points. Owner suite: `inventory.portability_contract`.
- Harness maintainability: Dart harness files should stay below the 500-line preferred target and must stay below the 1000-line hard ceiling while reporting over-target files as refactor candidates. Owner suite: `inventory.harness_maintainability_contract`.
- Release gates and baselines: Release gates use strict profile budgets, baseline diff checks, known-debt docs, and pack-health artifacts before release. Owner suites: `inventory.release_manifest` and `inventory.baseline_contract`.

## Structured Parser Result Contract

Future inventory, maintenance, estimate, job, invoice, and fleet workflows must consume one review-only parser candidate contract instead of coupling parser output to UI screens. The result contract vocabulary is intentionally broad so the UI can change without breaking parser evidence.

Required candidate fields or explicitly mapped equivalents: `rawLine`, `cleanedLine`, `merchantGuess`, `detectedTrade`, `detectedCategory`, `detectedSubcategory`, `detectedSystem`, `detectedItemType`, `canonicalItemId`, `canonicalItemName`, `material`, `composition`, `size`, `dimensions`, `length`, `width`, `height`, `diameter`, `schedule`, `gauge`, `rating`, `color`, `finish`, `variant`, `quantityPurchased`, `packageQuantity`, `stockQuantityCandidate`, `unit`, `unitPrice`, `lineTotal`, `matchedAliases`, `matchedMerchantRules`, `matchedParserPack`, `possibleMatches`, `confidenceScore`, `confidenceReasons`, `warnings`, `missingFields`, `reviewStatus`, and `suggestedInventoryAction`.

Field source attribution vocabulary must stay explicit: `fieldSource`, `sourceAttribution`, and `evidenceSource` identify whether each field came from raw receipt text, normalized text, merchant rules, parser-pack metadata, trusted catalog identity, generated parser evidence, learned local correction, or manual user correction. This keeps every accepted value explainable and reversible.

Parser candidates remain review-only. `possibleMatches` must carry ranked alternatives when ambiguity is realistic, and `missingFields` must explain what evidence is absent before a user approves, edits, ignores, or routes the line to a job/estimate/inventory workflow.

### Economical Expansion Path

The economical path is not one giant harness run. Build and run the harness in layers:

1. Keep the shared harness and reports stable with the cheapest sanity tests.
2. Prove parser-result safety, redaction, no-live-services, and review-only behavior.
3. Expand one trade pack at a time, starting with residential Plumbing Core.
4. Generate catalog items and synthetic fixture cases in large local batches, then run targeted behavior tests against that batch.
5. Promote only passing, reviewed fixture families into full/release shards.
6. Use the Mac Mini or CI-style full/release shard runner only after Windows smoke and focused behavior tests are clean.

## Shared Category Harness

The QA harness core lives under `test/support/qa_harness/` and is intentionally category-neutral. Inventory/Work Supplies plugs into it through `test/support/work_supply_parser_qa/`.

Maintenance, estimates, jobs, invoices, fleet inventory, or future catalog categories should reuse the same core report/result/redaction/suite runner and add their own category-specific suites and fixtures. Do not duplicate the whole harness for each category.

Every category suite must keep these contracts:

- Reports are redacted at the shared model layer before JSON or summary output.
- Smoke tests avoid expensive parser loops and prove loader/schema/security/report wiring.
- Full tests run semantic parser expectations against bounded fixture/generated batches.
- Release tests run strict gates and fail on blocking accuracy, safety, privacy, schema, or performance regressions.
- No test profile may hit live Firebase, cloud OCR, camera, Expenses, or production network services unless a future explicit integration profile is created and separately approved.

## Run Modes

Smoke profile is for fast daily development. It proves the harness, catalog schema sampler, alias sampler, fixture loading, generated-case building, grouped reporting, JSON output, and privacy-safe report path are working without running the most expensive semantic parser calls.

Full profile is for deeper local or Mac Mini runs. It runs the semantic parser assertions for dangerous words, golden fixtures, and generated catalog cases.

Release profile plus strict mode is for release gates. Any accuracy, safety, privacy, or schema failure becomes a test failure.

Every full harness run automatically appends `qa.threshold_gate` unless `PARSER_QA_SUITES` is used to run a targeted suite list that omits it. Add `qa.threshold_gate` to the suite list when a targeted run should still enforce profile budgets.

The `quick` preset must stay lightweight and avoid suites that intentionally load or scan the full catalog. Catalog-impact suites such as `inventory.changed_item_impact` belong in the `fixtures`, `catalog`, full, release, or explicit targeted runs.

Full/release orchestration contract:

- `full-profile timeout guard`: if a bounded full run hits an external command cap, do not treat the missing report as success. Record the timeout, rerun the timed shard by `PARSER_QA_SUITES`, and keep the previous `latest_work_supply_inventory_parser.json` as resume evidence only after confirming its timestamp and profile.
- `release shard strategy`: run one shard at a time for release validation, usually `quick`, `fixtures`, `catalog`, targeted parser-call suites, and strict release threshold shards. Each shard must include `PARSER_QA_PROFILE`, `PARSER_QA_MAX_GENERATED_CASES`, `PARSER_QA_MAX_FAILURES_PER_SUITE`, optional `PARSER_QA_SUITES`, and `qa.threshold_gate` when profile budgets should apply.
- Windows smoke should remain the fast local safety path. Mac Mini deeper runs should handle full/release parser-call sweeps when Windows command caps or slow Flutter startup make local full sweeps impractical.
- Each shard writes timestamped artifacts and latest aliases under `build/parser_qa_reports/`, including `latest_work_supply_inventory_parser.json`, so the next pass can inspect resume evidence without guessing what completed.

Default profile budgets:

- `smoke`: no critical failures, total runtime under 120 seconds, catalog schema sampler under 90 seconds.
- `full`: no critical or error failures, warning budget capped for known catalog-quality debt, total runtime under 10 minutes, and parser-call suites should stay above their minimum checks-per-second budgets.
- `release`: zero actual failures, zero critical/error/warning failures, total runtime under 10 minutes, and parser-call suites must stay above their minimum checks-per-second budgets.

`PARSER_QA_CATALOG_SCHEMA_SAMPLE_LIMIT` and `PARSER_QA_ALIAS_SAMPLE_LIMIT` control smoke-profile sampling for the two broad catalog-scanning suites. Full and release profiles still scan all catalog rows. Sampling does not avoid the first catalog construction cost, but it keeps smoke scan work explicit and adjustable.

`PARSER_QA_MAX_FAILURES_PER_SUITE` caps displayed failures per suite while preserving each suite's actual failure count. Use it to keep massive parser QA runs readable without hiding the true number of failures from threshold gates and reports.

`PARSER_QA_BASELINE` accepts a path to a reviewed redacted JSON report. Baseline comparison should fail or warn when coverage drops, suites disappear, actual failures increase, error/critical severity counts regress, or selected runtime metrics such as `coldStartMs` and `warmCacheMs` exceed their reviewed tolerance. Do not use baselines to bless bad output without reviewing why the result changed.
