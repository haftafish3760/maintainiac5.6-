# Firebase Abuse Prevention Plan

Maintainiac must protect user data and protect the owner's Firebase bill. UI
hiding is never the security boundary. Every hosted feature must be guarded by
Firebase Auth, App Check, Security Rules, server-side quota checks, and billing
monitoring.

## Launch Defaults

- Free users get 25 MB hosted cloud data per month until changed.
- Free users get 1 export per month until changed.
- Offline-only users can keep local Hive records without hosted sync.
- Hosted sync, proof uploads, exports, invites, AI, and customer portal sharing
  must be opt-in, metered, and revocable.
- Hosted backup covers mileage, expenses, receipts, jobs, estimates, invoices,
  inventory, maintenance, vehicles, employee permissions, calendar records,
  settings, audit events, exports, and customer portal records.
- No live Firebase load or abuse test runs without an explicit capped plan.
- Free hosted account creation allows 2 accounts per app install and 2 accounts
  per coarse IP window before additional verification is required.

## Account And Bot Abuse Layers

1. Require Firebase Auth for hosted features.
2. Allow only Google Sign-In and Apple Sign-In for hosted accounts.
3. Keep email/password, email-link, phone/SMS, and anonymous sign-in disabled
   for release. Employee and customer email addresses are contact/invite fields,
   not Maintainiac login providers.
4. Avoid SMS as the default MFA method because it is weaker and can create cost
   and SIM-swap risk. Prefer provider-managed security from Google and Apple.
5. Use Firebase Auth blocking functions after upgrading to Identity Platform:
   - `beforeCreate` checks account creation risk.
   - `beforeSignIn` checks blocked users, disabled orgs, and suspicious device
     state.
   - Provider allowlist checks reject anything except Google and Apple.
   - New account creation rejects or challenges app installs and coarse IP
     windows that exceed the launch thresholds.
6. Track abuse signals with privacy limits:
   - Firebase UID.
   - Org ID.
   - App installation ID generated by the app and stored securely.
   - App Check app ID.
   - Coarse IP hash or prefix when available server-side.
   - Sign-in provider and timestamp.
   - Normal product analytics stays anonymous.
   - AI abuse and security telemetry keeps enough account, anonymous analytics,
     install/device, app version, platform, rough region, task type, abuse
     reason, and action data to enforce bans and rate limits.
7. Never present this as user tracking. The purpose is fraud prevention,
   security audit, and account safety.

## Account Creation Gate

Account creation must be enforced server-side. Client checks can explain a
decision, but they are never trusted.

Modern Android and iOS do not give normal apps a permanent, trustworthy hardware
device ID. The release design must use layered signals instead of pretending one
magic device identifier exists.

Recommended first-release gate:

- Allow account creation only from Google or Apple Sign-In.
- Require valid Firebase App Check for hosted account creation.
- Generate a random app installation ID and store it in secure device storage.
- Send that install signal only to the account creation function over TLS.
- Hash the install signal server-side with a secret salt before storing counters.
- Allow the first 2 hosted free accounts per app installation hash.
- Allow the first 2 hosted free accounts per coarse IP hash/window.
- After either threshold is reached, require additional verification before
  allowing another account from that install or IP window.
- If either signal reaches 6 accounts in the review window, block signup and
  require manual review before more hosted accounts are created.
- Store abuse counters in server-managed Firestore documents only. Clients must
  not read or write install counters, IP counters, review queues, risk scores,
  or abuse flags.
- Store a salted hash or coarse prefix for IP-derived signals, not raw IP
  addresses in client-controlled documents.
- Combine the install hash, App Check app ID, provider ID, coarse IP window,
  failed attempts, invite activity, and storage/export usage before deciding
  whether to allow, challenge, block, or queue manual review.

## Device And App Verification

- Add Firebase App Check before launch.
- Android release builds should use Play Integrity.
- iOS release builds should use App Attest where possible, with DeviceCheck as
  fallback.
- Web should use reCAPTCHA Enterprise when the website/customer portal exists.
- Debug App Check providers are allowed only in dev builds and must never ship.
- Enable enforcement before public launch for mobile-only Firestore, Storage,
  and callable Cloud Functions after confirming metrics.

## Firebase Console Auth Setup

- Enable Google Sign-In.
- Enable Apple Sign-In.
- Disable Email/Password.
- Disable Email Link.
- Disable Phone.
- Disable Anonymous.
- Do not add social providers beyond Google and Apple for release one.
- Keep any employee/customer email fields as contact data only.

## Server-Side Quotas

Client code must never be trusted to enforce paid/free limits. Quotas are
checked in Cloud Functions using transactions.

Recommended monthly usage document:

```text
usage/{uid}/months/{yyyyMM}
```

Fields:

- `cloudBytesUsed`
- `uploadCount`
- `exportCount`
- `aiInputTokens`
- `aiOutputTokens`
- `functionCallCount`
- `lastQuotaResetAt`
- `plan`
- `blockedReason`

Free plan checks:

- Reject uploads when `cloudBytesUsed + incomingBytes > 25 MB`.
- Reject exports when `exportCount >= 1`.
- Reject AI calls when the user's free allowance is exhausted.
- Reject suspicious account creation when one install/device creates too many
  accounts in a short window.
- Reject or challenge suspicious account creation when one coarse IP window
  creates too many accounts in a short window.

All quota increments must happen on the server in the same transaction that
creates the upload/export/AI work request.

## Upload And Export Safety

- Do not allow direct unlimited Cloud Storage writes from the app.
- The app requests an upload session from a callable function.
- The function checks Auth, App Check, org membership, plan, monthly bytes,
  MIME type, file size, and module permission.
- The function creates a short-lived upload grant document.
- Storage Rules allow a write only when the matching grant exists and the file
  metadata matches the grant.
- Exports are generated through a callable function, not raw client writes.
- Export functions must set max instances, timeouts, and per-user rate limits.
- Large exports should be queued and cancellable.

## Firestore And Storage Rules

Rules must enforce:

- Deny by default.
- User can read only their own `users/{uid}` document.
- Org data requires active membership.
- Employee access requires both membership and permission.
- Helpers cannot read owner financial summaries by default.
- Clients cannot write usage counters, plan fields, role grants, billing fields,
  or official trade packs.
- Members cannot create records with `createdByUid` for another user.
- Storage reads/writes require active org membership and module permission.

Rules are necessary but not enough for quotas. Monthly totals and abuse counters
must be enforced by Cloud Functions because rules cannot safely aggregate usage
across many documents/files.

## Cloud Functions Safety

Every callable function should:

- Require Auth.
- Enforce App Check.
- Verify org membership and permission.
- Check and increment usage quotas server-side.
- Use strict input schemas.
- Reject unknown fields.
- Set timeouts and memory intentionally.
- Set `maxInstances` for expensive functions.
- Be idempotent where retries are possible.
- Write an audit event for security-relevant actions.

Sensitive functions should also use App Check replay protection when practical,
especially exports, invites, upload-session creation, and AI calls.

## AI Abuse / Jailbreak Enforcement

AI assistance must be protected before it is enabled for users. Anonymous-only
analytics is not enough for abuse/security events because one abusive account or
one device install can burn the AI budget, attack prompt boundaries, or try to
reach private data.

AI abuse/security telemetry may store:

- account ID
- anonymous analytics ID
- app installation ID
- hashed device signal when available
- app version
- platform
- coarse IP region when available server-side
- server-side request timestamp
- AI task type
- abuse reason
- action taken
- attempt count and risk bucket

AI abuse/security telemetry must not store:

- raw prompt text
- receipt text
- OCR text
- customer names
- addresses
- phone numbers
- emails
- invoice text
- notes
- private user content

The client may pre-screen obvious abuse patterns and queue safe telemetry, but
server-side Cloud Functions are the authority for enforcement. Server-side
actions must support:

- suspend AI access for one account
- suspend account
- ban app installation ID or device/install signal
- block new accounts from a banned install signal
- rate limit one install/device signal
- queue admin review in Command 1

Every enforcement action must be written to an admin audit log with who/what
changed, old value, new value, reason, and timestamp.

## Firebase Bill Protection

- Use separate Firebase projects for dev, staging, and production.
- Never stress test production first.
- Use emulator tests for unlimited security and rules testing.
- Use tiny capped live smoke tests only after explicit approval.
- Configure Google Cloud budget alerts before live testing.
- Add logs-based alerts for spikes in reads, writes, function invocations,
  storage bytes, auth account creation, and failed App Check verification.
- Keep a manual kill switch for hosted sync, exports, AI, and customer portal
  sharing.
- Prefer hard per-user quotas in code over hoping billing alerts arrive in time.

## First Release Abuse Limits

Suggested starting values:

- Free cloud storage: 25 MB per user per month.
- Free exports: 1 per user per month.
- Free AI: disabled until backend metering exists.
- Max new accounts per app install: 2 per rolling 30 days before additional
  verification.
- Max new accounts per coarse IP window: 2 per rolling 30 days before
  additional verification.
- Manual review threshold: 6 accounts per install or coarse IP window.
- Max invite attempts per owner: small daily limit until verified.
- Max failed sign-ins per account/device/IP window before cooldown.
- Max upload file size: smaller than the monthly quota, adjusted by receipt
  proof needs.

These are product settings, not hard-coded forever. They should live in a
server-controlled config document or Remote Config equivalent, but clients must
not be trusted to enforce them.
